Capstone, team of three

Taking a server room from zero monitoring to 235 live metrics

The school's production server had no monitoring at all. I owned the infrastructure: getting our monitoring VM onto the right network, building the stack, and turning on SNMP safely.

  • Solved the blocker. The VM was stuck behind NAT, so I bridged a second NIC onto the server subnet and got 1.5 ms with zero packet loss.
  • Built the stack from scratch on Kali: Zabbix 7.0, Apache, MariaDB, and PHP.
  • Least privilege on a live server. I opened only UDP/161 in iptables, limited SNMP to the local /24, and made it survive reboots.

Firewall and network design

A segmented network where the DMZ can't reach the LAN

I designed a three-zone network on pfSense so public-facing servers live in a DMZ, and a compromise there can't move sideways into the internal network.

  • Segmentation that holds. Web traffic is allowed into the DMZ, and DMZ-to-LAN traffic is blocked.
  • Network services. DHCP with MAC reservations for servers, and BIND DNS zones with A, MX, CNAME, and PTR records.
  • Hardened. I turned off unused DNS and DHCP services, then proved isolation with rule testing and log review.
ToolspfSense 2.7, BIND, DHCP, VMware
ZonesWAN, LAN 192.168.1.0/24, DMZ 192.168.2.0/24

Detection engineering

Attacking my own web server, then catching every attack

In an isolated lab I launched real denial-of-service attacks, wrote the detection rules, and compared each attack on the wire against a clean baseline.

  • 3,262 Suricata alerts from my custom rules, covering SYN floods, connection floods, and Slowloris.
  • Proved the impact. The slow-HTTP attack dropped the server from 500 available connections to 0 in six seconds.
  • Evidence kept. PCAPs, alert logs, and a written report are published so the findings can be replayed.

Service monitoring

A known-good baseline, so problems stand out

An analyst can only spot an anomaly after defining normal. I built PRTG sensors that each watch a different way a service can fail.

  • Three failure modes watched: connectivity with Ping, name resolution with DNS, and availability with HTTP.
  • Baseline measured: 7 ms latency with no packet loss, 92 ms DNS resolution, and a 482 ms page load, all at 100% uptime.
